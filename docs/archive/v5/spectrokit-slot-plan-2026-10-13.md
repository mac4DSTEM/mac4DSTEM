## 0. Facts that change the ADR's picture

1. The moving set is 51 files, 9 202 lines: `Core/Spectroscopy/**` minus `Registration/` (47 files) + `Core/Data/VeloxEMDReader.swift` (1 333) + `Core/Data/HDF5Types.swift` (128). Imports: Foundation, Accelerate (FitLinearAlgebra only), CryptoKit, Darwin. No SwiftUI, no AppState, no Session. 39 commits touch these paths (cheap history).
2. **Every declaration is `package`, none `public`** (1 097 `package` lines in the set; XRayLineData is 960 data lines with 0). `package` does not cross SwiftPM packages (mac4DSTEM's package name is `mac4dstem`; SpectroKit differs), so everything the app/Registration/Session/tests call must become `public`.
3. **`HDF5Types.swift` is not purely standalone.** It holds three things: the typealiases `hid_t/herr_t/hsize_t` (lines 4-6, used by H5Reader, BraggVectorEMDWriter, Velox), `SessionSidecarFormat` (lines 8-76: the `.mac4dstem.h5` sidecar identity; 4D; used by H5Reader, SessionReplayRecord, SessionLineage, BraggVectorEMDWriter, Support/ResultExport.swift and 5 test files), and `HDF5Serial` (lines ~78-128). `SessionSidecarFormat` must be split out (stays in `Core/Data`) before the freeze. ADR 064/CLAUDE.md name the whole file as moving; that is wrong for this type.
4. **`HDF5Serial` is process-wide shared with 4D code**: H5Reader (11 sites: `H5Reader.swift:195,278,290,296,459,490,540,738,750,760,782,1049`), BraggVectorEMDWriter (~25 sites incl. `:345,1613-1699,3079`), VeloxEMDReader (`:640,863,876,906,1162,1189,1220,1252,1262,1282,1323`), tests (SwiftUIReviewBTests:47, SidecarAttributeGuardTests:127, ReviewHDF5GuardTests:133), tools (`hdf5-exit-race-test`, `dm4-parity-probe/subsample.swift`). After the split the lock's home must be SpectroKit (`SpectroCore`, `public`), and mac4DSTEM's 4D readers/writer import it. Two copies of one lock = the crash `tools/hdf5-race-probe` reproduces. macTEM contract (§2 "Threading") asks for exactly this.

## 2. `unsafeFlags` (Package.swift)
Three, all `mac4DSTEM/Package.swift`:
- `DSTEMCore` line 34: `.unsafeFlags(["-Xcc", "-DACCELERATE_NEW_LAPACK"])`. Why (comment 18-33): exposes `__LAPACK_int` and the non-deprecated LAPACK prototypes; needed by `Core/Analysis/DiffractionEmbedding` (dsyevd_) AND `Spectroscopy/Fit/FitLinearAlgebra.swift` (`dgelsy_` :87-94, `dgeqrf_`, `dorgqr_`, `dtrtri_` :98-125; header comment :10-11). Real need: yes, but only for the macro, not for -Ounchecked or C flags. Other users of the same flag (stay): DiskDetection, DPC, ParallaxAlignment, FFT1D/2D, OrientationMatcher (grep `__LAPACK_int|ACCELERATE_NEW_LAPACK|import Accelerate`).
- `DSTEMCore` line 41, `DSTEMSession` line 54, `DSTEMTraining` line 70: `.unsafeFlags(["-O"], .when(configuration: .debug))`. Why: package Debug is -Onone; owner runs Debug; Friedel FFT crawled (Gate D 2026-09-30). For SK: Velox decode (408 M values, 3 passes) and fits are the hot loops; Debug cost: unknown (macTEM contract §3.1 asks for a timing of the 816 MB file in a throwaway Debug consumer).
Replacement for SpectroKit (zero unsafeFlags):
1. **LAPACK via a small C target** (`CSpectroLAPACK`): `Sources/CSpectroLAPACK/lapack_shim.c` with `#define ACCELERATE_NEW_LAPACK` before `#include <Accelerate/Accelerate.h>`, exporting 4 plain-C wrappers (`int sk_dgelsy(...)`, `sk_dgeqrf`, `sk_dorgqr`, `sk_dtrtri`) taking `int`/`double*`; the public header includes NO Accelerate, so Swift never sees two Accelerate configurations. (A header that defines the macro and then includes Accelerate, imported next to `import Accelerate`, risks a conflicting-module-config error: unknown, test in S3; the wrapper form avoids it.) `FitLinearAlgebra.swift` then calls the wrappers; `import Accelerate` and `__LAPACK_int` leave the Swift file. Optionally `cSettings: [.define("ACCELERATE_NEW_LAPACK")]` instead of the in-source define. `__LAPACK_int` is 32-bit `int` without ILP64, so the wrapper signatures are exact.
2. Debug -O: drop it from the manifest. Options (unknown which works; test in S3): (i) measure first, may not matter; (ii) consumers set optimisation for the package in their project (macTEM contract already assumes this); (iii) `@_optimize(speed)` on the 3-4 hot functions (VeloxStreamDecoder.scan/buildEventStore, `EDSFit`, `LeastSquaresFit`) - whether Debug honours it: unknown.
Proving no number moves: (1) at the freeze commit dump every FitLinearAlgebra consumer's output as hex doubles (fixtures: `eds-fit-exspy-7185a4d1.json`, `eds-quant-pins-exspy-7185a4d1.json`, `eds-pins-...json`, `eds-weakline-sim`, `eds-proposer-sim`, `eds-unlisted-sim`, `eds-realistic-l-sim`, `eds-absorption-truth`) and compare **bit-identically** after (same LAPACK routines, same arguments); (2) unit tests `SpectroscopyFitTests` (27), `SpectroscopyQuantTests` (18), `EDSQuantPinsTests` (8), `SpectroscopyProposerTests`, `SumColumnDedup`, `SumEscapeIdentical`, `SpectroscopyUnlistedLineTests`, `SpectroscopyFitRangeTests`; (3) mutation: break one shim argument (e.g. rcond) and confirm red.

## 3. The HDF5 lock
- Defined: `HDF5Types.swift:~78-128` (`HDF5Serial`, recursive `NSRecursiveLock`, `run`, `acquire/release`, `installExitBarrier` via atexit). Contract: "NEVER held across an await".
- Velox decode today holds it **for the whole logical operation**: `readSpectrumImage` `VeloxEMDReader.swift:906` `try HDF5Serial.run {` opens at 906 and spans to ~1052: `VeloxFile` open/readString/children/open dataset, **`lengthAndMarkers` pass (:963 -> blockSource :1056-1075)**, `buildEventStore` (two more full passes via `BlockSource`, `:242,260`; 408 M values, 64 MB blocks `blockValues = 32<<20` :1054) and `readScanImage`. Other `run` sites (863, 876, 1162, 1189, 1220, 1252, 1262, 1282, 1323) are short (a metadata JSON/frame) except `markersPerFrame` (:1219) and `streamLengthAndMarkers` (:1251), which also stream the whole data.
- Minimal change: (a) remove the outer `HDF5Serial.run` in `readSpectrumImage`, `markersPerFrame`, `streamLengthAndMarkers`; (b) put the lock inside `VeloxFile`: `init` (:671-678 incl. `VeloxHDF5.load()`), `deinit` (:679 `h5fclose`), `exists`, `children`, `open`, `close`, `readString`, `readSlab` (:~733), `readMetadataJSON` each wrap their libhdf5 calls in `HDF5Serial.run {}` (recursive, so nested use by the short entry points stays valid); (c) `blockSource` (:1056-1075) then holds the lock only inside `readSlab`, and the decoder's per-value loop (`scan`, :187-200) runs unlocked. The dataset handle stays open between blocks (legal: the lock guards calls, not handles). Lock hold <= one 64 MB `H5Dread`. (d) A test: a second thread takes `HDF5Serial.run` while a decode runs; the wait must be bounded by one block (mutation: restore outer lock -> red). Also reconcile `VeloxFile`'s doc comment (:582, :665 "callers hold the lock across a whole logical operation").
- Risk: HDF5 `Threadsafety OFF` - the unlocked stretch touches no HDF5 state (pure buffer decode). Quit barrier unchanged.
- **Home after split:** `SpectroCore` (`public`), because `H5Reader`/`BraggVectorEMDWriter` (4D) and macTEM's V1-2 sidecar writer must take the same lock. mac4DSTEM's `DSTEMCore` gains a SpectroKit dependency solely for this (+ hid_t aliases); `tools/hdf5-race-probe`, `hdf5-exit-race-test`, `dm4-parity-probe` compile it from the SK checkout (needs a SpectroKit group in `tools/lib/sources.manifest`; currently `readers`/`sidecar` groups list `Core/Data/HDF5Types.swift` at manifest lines 132, 136, 382).

## 7. Name collisions with macTEM and Bundle.main
