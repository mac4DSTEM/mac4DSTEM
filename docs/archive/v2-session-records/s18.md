## What shipped

### 1. The colorbar and the scale bar share one bottom row

`UI/ScaleBarView.swift` gains `PaneBottomOverlay`, used by both
`StemImageView` and `DiffractionView`. `ViewThatFits` keeps the bar leading and
the legend trailing while both ideal widths fit the pane, and stacks them
otherwise. The wide case is deliberately unchanged — a fix that stacked them
always would pass a glance at a narrow pane and waste a third of every normal
pane's bottom edge, which is what Track B row F1.32 is written to catch.

The result pane's three trailing legends — the DPC colour wheel, the IPF key,
the scalar colorbar — moved into that row's trailing slot as a `VStack`. Their
conditions are preserved verbatim and in order; only the overlay-inset padding
moved out to the container. **Correction (Gate A, same day):** the first version
of this record, and the comment in the code, justified the `VStack` by saying
two legends that matched at once would now both be legible instead of
overlapping. **That state cannot occur** — all three are mutually exclusive by
construction, and claiming a benefit that never fires is the defect S3 removed
when it dropped `Residency`'s dead `String` conformance. The `VStack` is
structural, nothing more.

### 2. #38 — the scroll monitor is scoped by geometry, not by hover

`addLocalMonitorForEvents` is application-wide: while installed it sees every
scroll in every window and, by returning nil, swallows it. Hover was the only
thing deciding whether it was installed, and hover is not a reliable exit
signal — another window coming forward, a sheet opening over the pane, Mission
Control, or a fast exit can all leave `.onContinuousHover` never reporting
`.ended`. The pane then ate the wheel for the whole app.

`ZoomPanModifier` now keeps a passthrough backing view (`PaneGeometryProbe`,
`hitTest` returns nil so it can never take a click) and consumes a scroll only
when it landed inside that view's `visibleRect` in that view's own window;
everything else is returned untouched. `visibleRect` rather than `bounds` so a
pane clipped by an enclosing scroll view does not fight the scroll view hiding
it; the window comparison covers sheets and popovers without a special case.
Hover still gates installation, so the number of live monitors is unchanged —
but a monitor that outlives its hover is now inert instead of destructive.

### 3. The sidebar dataset card names its axes

The card read `106 × 153 scan` while the inspector read
`Scan (Ry x Rx)  153 x 106` and `Shape  153 x 106 x 256 x 256`.

**The second look the entry asked for: both orders are correct and neither
should change.** A number printed beside an image should read the way the image
draws; a row labelled with its own axes should read the way the array is
indexed. Forcing one order on all three would make the card disagree with the
picture next to it — the same defect pointing the other way.

The real defect is narrower than "two orders": the card carried **no labels**,
so a reader had two numbers, no way to tell which convention either used, and
nothing to reconcile them with — the tag-day shape of a summary contradicting
its own detail line. The card now reads
`106 × 153 scan (Rx × Ry)  ·  256 × 256 detector (Qx × Qy)`; the inspector is
untouched.

The longer string was a real risk to S17's freshly-pinned sidebar geometry, so
it was **measured, not assumed**: `unit` is exit 0 after the change, with
`testEveryNonQuarantinedWorkspaceSidebarFitsItsColumn` and
`testSidebarDocumentRoughlyFitsItsColumn` both still passing.

### 4. The comparison pane redraws when its product changes

`ProductWorkspaceViews.swift` passed the literal `0` as `contentVersion` (at
`:719` before this change; the live call site is now `:805`).
`MetalImageView`'s Coordinator re-uploads only when that value changes and
starts at `Int.min` — so the **first** image uploaded and every later one was
silently dropped. Swapping which saved product sits in slot A left the pane
showing the previous product's pixels **under the new product's name**. That is
the failure this app exists to prevent, and it is silent. Same class S4 fixed
for the configurator and the inspector; this call site was missed.

A second defect lived in the same three lines: the payload rendering and
`ProductComparison.difference` ran inside `body`, and `body` re-runs on every
`onContinuousHover` cursor update — three O(width × height) normalizations plus
a full image subtraction **per pointer move**.

Both are fixed by building the panels once, in `init`: SwiftUI re-runs `init`
only when the parent hands over different products, which is exactly when the
pixels and the version change. The work moved into a new internal
`ComparisonPanel` type rather than a private method, so the version rule is
reachable from a test — a private helper inside a private `View` can only be
checked by looking at it.

**The RGBA half is the same defect one payload deeper.** An RGBA product renders
through its packed bytes and carries an all-zero `pixels` array, so a version
derived from `pixels` alone is identical for every same-sized RGBA product — a
hexagonal IPF map and a DPC colour wheel of equal dimensions would version the
same. `ComparisonPanel.version` folds the bytes in.

### 5. `pattern(ry:rx:)` is served from the resident cube

It read through the reader unconditionally, so browsing diffraction patterns
stayed disk-bound while the Performance panel read "Resident" — the indicator
over-promised. A pattern is now sliced out of the cube at
`(ry * rx + rx) * qy * qx`, and deliberately **not** cached: the slice is a
memcpy out of memory already held, so caching would duplicate up to 96 patterns
of the resident cube for no saved I/O.

The equality this rests on was **not previously asserted anywhere**: the cube is
filled by `readScanTile` while the streaming path answers with `readPattern`,
and nothing in the repo checked that a reader's two entry points agree pattern
for pattern. The harness now does.

### 6. The resident staging copy is gone

All four tiled reducers — `tiledDPStatistics`, `tiledDiffraction`,
`tiledMeasuredOrigins`, `tiledCenterOfMass` — went buffer → `[Float]` → new
`MTLBuffer` for every tile even when the cube was already in memory: ~0.375 ×
working set of pure waste, found by adversarial review 2026-08-17.

They now go through `TileGPUSource`, which binds the resident buffer at the
tile's byte offset via a new `cubeOffset:` on the four `MetalEngine` entry
points; the streaming path is unchanged and still prefetches.

**The tiling is deliberately unchanged** — same ranges, same partials, same
combination order. That is what keeps the two float-order-dependent reductions
bit-identical rather than merely close, and so keeps
`tools/virtual-detector-residency` asserting exact `==` instead of a tolerance.
Offsets are whole scan rows, so Metal's 4-byte `device`-address-space alignment
is automatic.

`virtualDetector` and `virtualImage` did **not** get the parameter: their tiled
caller already has a whole-cube resident fast path, so a `cubeOffset` there
would be a parameter nothing could pass.

### 7. #37 measured

Three new benchmarks in `tools/performance-baseline` (a non-gating mode, so no
suite pays for them). 64×32×128×128 synthetic cube, 4-row tiles (16 tiles), M3,
7 repeats after 1 warmup:

| what | median | min | max |
|---|---|---|---|
| streaming, best case (cancel at a tile boundary) | **0.006 ms** | 0.004 | 0.011 |
| streaming, **bound** (one whole tile) | **5.4 ms** | 4.0 | 6.7 |
| resident, **bound** (the one indivisible dispatch) | **13.2 ms** | 11.1 | 16.0 |

**The check granularity is not the problem.** A user waits at worst one tile and
on average half of one — single-digit milliseconds, which nobody would call "a
long time". The cost must therefore be in the part this measurement excludes:
the source is synthetic and in memory, so each tile is dispatch-only and the
**read** half of the per-tile bound is missing. On a real file that read is the
whole story and over a NAS it dominates. **#37 is an I/O item and belongs with
S9**, not with the cancellation checks.

**The 2026-08-17 review's counter-argument is confirmed.** Resident cancellation
is coarser, by 2.5× here. The harness found this the hard way: its first version
cancelled after the first progress tick, and on the resident path the only tick
is `progress?(1)` after the dispatch has already finished — it arrived at
21.36 ms of a 21.36 ms pass. There is no mid-pass to cancel into, which is why
the two paths are now measured differently and each is named for what it
actually measures. The instrument itself had to be rebuilt once for the same
reason: the first `ProgressGate.wait()` blocked on a semaphore, and the thread
hop out of and back into the cooperative pool cost enough that the whole pass
finished inside the wait.

## Gate A — ran 2026-08-27, 14 agents over 5 lenses

**PASS on the code. FAIL on the verification artefacts.** 15 raw findings, 2
survived adversarial verification, 2 refuted. Nothing in the shipping UI diff
was shown to draw the wrong thing; both survivors were in what this session
wrote *about* the change.

**1. CRITICAL — Track B row F1.36 could not pass on any dataset, and it was
routed to sitting 3, the scarcest sitting in the project.** The row told the
owner to click "Load into memory". **There is no such control.**
`DatasetResidency.mode` is `.streamed` (`App/DatasetResidency.swift:34`); its
only mutator `request(_:on:)` has **no caller anywhere under `mac4DSTEM/`** —
only `mac4DSTEMTests/` and `tools/`; `summary` therefore always returns
"Streaming" (`:62`), so even the `isResident`-gated "Release cube" button
(`UI/InspectorPanels.swift:33`) never appears. `AppState.preloadResidentCube()`
states it in its own comment: *"nothing in the UI requests `.resident` yet"*
(`App/AppState.swift:2701-2703`). Verified independently before acting.

This is the F1.1 failure repeated — a row queued ahead of the affordance it
observes — and the row's own escape hatch made it worse: told to mark it
BLOCKED without a big cube, the owner would have logged BLOCKED *for the wrong
reason*, leaving a row that looked un-driven rather than un-driveable. **F1.36
withdrawn the same day it was written**, with the same reinstatement condition
F1.1 carries.

**The consequence runs past the row, and this session stated it wrongly twice.**
Both `Core/` changes only take effect on a resident cube, so **neither is
reachable in the shipping app today** — they are correct, tested, and currently
exercised only by harnesses. Two claims written in this session were false and
are now corrected: `open-items.md`'s "a property of a button the user pressed"
(there is no button), and this session's stated motivation for change A, that
the Performance panel "over-promised" by reading "Resident" while browsing was
disk-bound — **the panel can never read "Resident"**. The fix is still right;
the reason given for it described a state the app cannot enter. A separate
audit of what residency ships versus what a user can reach was commissioned on
the strength of this finding.

**2. HIGH — F1.32 quoted its 242/302 pt thresholds against the wrong width.**
The arithmetic was re-derived and confirmed correct, but `PaneBottomOverlay`
sits inside the ZStack pinned to `.frame(width: box.width…)` where
`box = fitted(in:aspect:)` (`StemImageView.swift:266,448`) — so `ViewThatFits`
decides on the **fitted image box**, not the pane. The row's primary procedure
(drag the divider to the 170 pt floor) still works, because `box.width` is never
more than the pane. What did not survive is the row's own second instruction: on
the rotated 200×50 scan the box is ~200 pt wide at *every* divider position, so
that pane is stacked always — and the row said to score both widths there. The
owner would have failed correct behaviour on the exact dataset the defect was
found on. Row corrected, and so was the comment it inherited the error from:
`ScaleBarView.swift` claimed the collision "is a property of the pane's width,
not of any one dataset", and both halves were wrong.

**Refuted, and worth recording because both proposed fixes would have made
things worse.** (a) "The narrow fallback right-aligns, so an over-wide legend
overflows the pane" — died on a misread: the container's `.frame(…, alignment:
.bottom)` is horizontally *centred*, the widest padded block is 162 pt against a
170 pt floor, and the deleted `.bottomTrailing` overlays already spilled 37 pt
one-sided, so the maximum excursion **decreased**; the proposed remedy would
have reinstated the larger one. (b) "`scrollLanded` has no fallback, so a probe
failure silently kills wheel-zoom" — died on reachability: the monitor and the
probe are `@State` on the same modifier, so there is no state where a live
monitor is gated by a window-less probe, and the proposed "fall back to
`bounds`" would reintroduce exactly what the code rules out in writing.

**Attacked and HELD.** All four `StemImageView` trailing-legend predicates and
both `DiffractionView` ones diffed character-for-character against
`git show HEAD:` — identical, same order, none lost or negated; the inset
arithmetic reconciles exactly, so the "wide case is pixel-identical" claim
stands. The container cannot expand the ZStack. `#38`'s fix holds against sheet
windows, two live monitors, leak/double-remove, hit-testing and Swift
concurrency. `ComparisonPanel.version` survived every attack including the
RGBA-vs-all-zero-scalar collision, which the reviewer verified *by arithmetic*
rather than by luck of constants. The axis labels reconcile with an untouched
inspector. F1.34 and F1.35 are driveable as written.

  benchmark takes a descriptor and a cube, so pointing it at a real file is a
  small change — S9's, with the NAS.
- **No harness in this repo exercises either change against a REAL reader**, and
  running `run-tests.sh all` would not change that. Established by reading the
  only candidate, 2026-08-27:

  `tools/real-data-acceptance` is in `all` but not in `scientific`, and it
  compiles every file S18 touched — `FourDArray.swift`, `VirtualDetector.swift`,
  `MetalEngine.swift`, `ResidentCube.swift` — against real HDF5 through a real
  `H5Reader`. But it never enters either changed path: it calls
  `reader.readPattern(...)` directly rather than `FourDArray.pattern(ry:rx:)`
  (`tools/real-data-acceptance/main.swift:91`), and it builds its `FourDArray`
  without ever calling `setResidencyRequest(.resident)` or `makeResident()`
  (`:156`), so its `tiledImage` call takes the STREAMING path. It would catch a
  compile break or a streaming regression and nothing else here.

  So the coverage splits exactly the wrong way for change A's central claim:
  the residency harness has both paths but a SYNTHETIC in-memory source whose
  `readPattern` and `readScanTile` both delegate to the same `LoadView` helpers,
  while the real-reader harness has a real `H5Reader` but never goes resident.
  **`readPattern` ≡ `readScanTile` is therefore asserted only where both sides
  come from one array** — the shape of the L3 self-consistency trap, and the
  thing the Gate B ground-truth lens was briefed to attack.

  Closing it would mean either making `real-data-acceptance` go resident and
  compare a few patterns, or a small real-reader case in the residency harness.
  Neither is in S18's bounded list; recorded rather than smuggled in.

- **`run-tests.sh all`** was not run. It remains S19's dependency and S19's job;
  `unit` and `scientific` are the two gates that cover this session's changes.
- **The `.automatic` residency sweep** is untouched and stays post-v2, but note

## Found in this session's own work, not yet fixed

- **The three new benchmarks hardcode `checksum: 0`, which makes a real guard
  vacuous.** `tools/performance-baseline/compare.py:35-47` intersects the
  benchmark key sets (so the additions do not break an older baseline — S20's
  release table is safe) and reports `checksum_before` / `checksum_after` as a
  workload-identity guard: it is what tells a reader that a benchmark quietly
  started measuring something else. With a constant 0 that guard can never
  fire for these three. The two *bound* benchmarks run a pass to completion and
  could checksum the produced `FloatImage`; only the cancel-latency benchmark
  genuinely has no output to hash, and that one wants a comment saying so
  rather than a silent zero. Not fixed here: verifying it means re-running
  `run-tests.sh benchmark`, which was not possible while the Gate B mutation
  sweep held the GPU, and landing it unverified is the habit this repo
  punishes. Owner: the session that next touches the baseline, or S20 when it
  records the release table.

## The skills, and one that fired correctly while I under-executed it

`pickup` and `diagnose` behaved. `closeout` behaved. **`track-b` fired at the
right moment, gave the right instruction, and I did half of it** — that is the
friction worth recording, because the skill is not at fault and editing it is
therefore the only way to stop the repeat.

Its rule 2 says: *verify each row against what the build actually does before
queuing it*, and it names the exact precedent — F1.1, withdrawn because it asked
the owner to watch a phase that could not run. I read that, queued five rows,
and verified **F1.32's arithmetic** while never checking that **F1.36's control
existed**. It did not. Same failure, same file, one session later, on a row I
pointed at the scarcest sitting in the project.

The gap is that "verify against the build" is ambiguous between two very
different checks: *is the expected result right?* (I did that) and *does the
affordance the row names exist at all?* (I did not). The second is cheaper and
catches the worse failure. **Proposed edit to `.claude/skills/track-b/SKILL.md`,
rule 2: require naming, for each row, the control the owner will touch and the
`file:line` where it is wired** — a row whose control cannot be cited is an F1.1
and does not get queued. That check would have killed F1.36 before it was
written, in under a minute.

Also worth carrying: the skill says the assistant never runs Track B. **That is
now only half true.** With Screen Recording and Accessibility granted, the
assistant drove F1.32 and F1.34 against the build under test and found a real
defect in this session's own work. The skill should distinguish rows that are
assistant-driveable (layout, text, presence/absence) from those that need the
owner (judgement, "does this read as trustworthy", anything on a multi-GB or
NAS dataset) — rather than implying none are.
