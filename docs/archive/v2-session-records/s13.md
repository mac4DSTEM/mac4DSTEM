## 0. Pre-registration — written 2026-08-28 BEFORE any measurement or code

S12 stated plainly that §3's two estimator checks are *"designed, not
prototyped — their discriminating power is asserted and S13's pre-registered
experiment may refute it."* §3.1 makes the threshold an explicit entry ticket:
*"The threshold must be measured, not invented … Inventing a number here would
reproduce exactly the failure mode S17 diagnosed."*

So the numbers below are written down before the harness exists. Anything the
experiments contradict is recorded as **refuted**, in place, not quietly
absorbed.

### E1 — the shell-consistency threshold (design §3.1)

**Question.** What value of `medianAbsoluteDeviationPixels / observedRadiusPixels`
(both already computed by `KnownCrystalQCalibration.estimate`) separates a sound
origin from a displaced one?

**Dataset.** `sim_Au_data_all_binned` — the only training dataset where Q
calibration currently runs end to end (S12 §7). One dataset gives a *curve*
under controlled displacement, not a population; that limit is stated in the
result, not papered over.

**Method.** Run the campaign's path — `OriginCalibration.tiledRun` → disk
detection → `BraggVectors.calibrated` → `estimate`. Then perturb
`calibration.origin.fittedX/Y` (the quantity a bad fit actually gets wrong;
`BraggVectors.calibrated` collapses peaks onto the *per-position fitted* origin,
so this is the true injection point, not `referenceOrigin`) in two arms:

- **Arm A — constant displacement.** Every fitted origin moved by the same
  (δ/√2, δ/√2), δ = 1, 2, 3, 5 px. This is the geometric-middle-fallback shape:
  a systematically wrong centre that does *not* vary with scan position.
- **Arm B — position-varying displacement.** Independent isotropic Gaussian
  jitter of RMS δ per position, δ = 1, 2, 3, 5 px, fixed seed. This is the
  contaminated-fit shape #29 describes.

**Predictions, in order of how much I expect to be wrong about them.**

1. **Arm B: MAD/observed rises steeply and monotonically with δ.** Predicted
   separation: the δ = 3 px value is **at least 3×** the δ = 0 baseline. If it
   is not, §3.1's statistic does not discriminate the case it was designed for
   and the design is refuted.
2. **Arm A: MAD/observed rises only weakly — I predict the δ = 5 px value stays
   below 2× the δ = 0 baseline.** If that holds, **§3.1's claim that the check
   "fires on the geometric-middle fallback too" is REFUTED**, and the design
   must be corrected rather than shipped. A constant offset shifts every
   position's innermost radius by nearly the same amount, which is what MAD is
   built to ignore.
3. **`observedRadiusPixels` collapses in BOTH arms once δ > `minimumRadiusPixels`
   (2 px).** With the origin displaced by δ, the *direct beam* sits at radius
   ≈ δ from the assumed centre and is admitted as the "innermost non-central
   peak". Predicted: at δ = 3 and 5 px the observed radius falls to within
   ±50% of δ, i.e. far below the true first-shell radius. If so, the
   **collapse is a stronger and more direct signal than MAD/observed for the
   constant case**, and the design should gain it.
4. **Candidate third check, measured here because it is nearly free:** the
   innermost shell radius must exceed the **probe radius**. A "reflection"
   closer to the centre than one disk radius is overlapping the direct beam and
   cannot be a resolved shell. Predicted: on unperturbed sim_Au
   observed ≫ probeRadius; at δ = 3, 5 px observed < probeRadius. This is
   dataset-independent and needs no threshold hunt if it separates cleanly.

**What would make me abandon §3.1 rather than tune it:** prediction 1 failing.
MAD/observed exists to catch the varying case; if it cannot, no threshold on it
is worth shipping.

### E2 — where a ceiling on the excluded fraction would go (design §6(b))

**Question.** The owner decided to ADMIT trimmed calibrations and show the
excluded fraction; whether there is a fraction above which the app should refuse
regardless of the residual is **open**, and S13 must measure rather than pick a
round number.

**What the existing numbers already say, and why the naive ceiling is wrong.**
S12 §1.2 measured trimming keeping **100.0%** on `downsample_Si_SiGe_exp` — the
dataset whose fit is *worst*. Broad measurement failure has no tail to trim, so
it excludes nothing. **The excluded fraction therefore does not separate good
from bad at all**; it cannot be the refusal statistic, and any ceiling on it
guards only the opposite end: a kept subset too small or too clustered to
constrain the fit.

**Method.** On all four training datasets, sweep the trim aggressiveness
(MAD multiplier k = 4.0, 3.0, 2.0, 1.5, 1.0) to generate a *range* of kept
fractions, and at each measure:

- kept fraction;
- **bootstrap SD of the fitted origin** — resample the kept positions with
  replacement, 200 draws, refit the plane, take the SD of the fitted origin
  across the scan. This is the fit's own uncertainty;
- **max extrapolation distance** — the largest distance from any scan position
  to the nearest kept position, in scan pixels, which is what actually goes
  wrong when the kept set is spatially clustered.

**The criterion, fixed now:** a ceiling is defensible at the kept fraction where
the bootstrap SD reaches **2 px** — #29 item 1's estimator-breakdown scale, the
point at which the fit's own uncertainty is as large as the error it exists to
remove. Not a round number, and not mine.

**Prediction.** **No defensible ceiling on the fraction alone will be found.**
A 3-parameter plane over thousands of positions is heavily over-determined, so I
predict the bootstrap SD stays **below 2 px even at kept fractions under 20%**
on every training dataset, and that the max-extrapolation-distance measure moves
first. If that is what the data says, the honest outcome is **ship without a
hard ceiling**, refuse on the robust residual, and report the fraction — which
is what §6(b) explicitly permits. If bootstrap SD *does* cross 2 px at a
reachable fraction, that crossing is the number, and it goes to the owner.

### Scoring the pre-registration

- **Prediction 1 — CONFIRMED, and by a wider margin than predicted.** Arm B's
  MAD/obs at δ = 3 is 0.3084 against a 0.0156 baseline: **19.8×**, where ≥ 3×
  was the bar. §3.1's statistic does discriminate the case it was designed for.
- **Prediction 2 — CONFIRMED, which means §3.1's own claim is REFUTED.** Arm A
  at δ = 5 gives MAD/obs **0.0121**, *below* the δ = 0 baseline; the largest
  value anywhere in arm A is 0.0564. The design says the check "fires on the
  geometric-middle fallback too, because a wrong centre makes the innermost
  radius track the true beam's offset." **It does not.** A constant offset
  shifts every position's innermost radius together, which is exactly what a
  median-absolute-deviation statistic is built to ignore. The design's sentence
  must be corrected, not shipped.
- **Prediction 3 — CONFIRMED.** Observed radius collapses toward δ once
  δ > `minimumRadiusPixels`: arm A 2.89 px at δ = 3 and 4.89 at δ = 5 (both
  within 4% of δ, not merely the predicted ±50%). The collapse is a stronger
  and more direct signal than MAD/obs for the constant case, and the design
  should gain it.
- **Prediction 4 — CONFIRMED and it is the cleanest separator measured.**
  obs/probeRadius is ≥ 3.35 on every sound sim_Au case and ≤ 0.81 on every
  collapsed one, with nothing in between. The threshold does not need fitting:
  **1.0**, because a reflection whose centre is closer to the origin than one
  probe radius has a disk overlapping the direct beam and is not a resolved
  shell. Physically derived, not a number anyone picked.

### The unpredicted result: §3.2 is refuted AS SPECIFIED, and repaired by the same run

The design says to "collect the innermost two radii per position and compare
median(r₂)/median(r₁) against g₂/g₁". Measured on healthy sim_Au that ratio is
**1.0205** against an expected **1.1547** — a 12% "mismatch" on the dataset
where everything is right. The cause: `Crystal.reflections` returns every
symmetry equivalent separately, all at the same |g|, and several equivalents of
the *first* shell are excited at one scan position, so r₁ and r₂ are usually two
peaks **of the same shell**. As written the check compares a shell against
itself and would fire on good data.

The repair is one added condition, and its size is **derived rather than
chosen**: r₂ must be the innermost radius at least `(g₂/g₁ − 1) / 2` larger than
r₁ — half the gap the crystal itself predicts, which the app already knows.

| separation | sim_Au ratio | Si_SiGe ratio |
|---|---|---|
| 0% (design as written) | 1.02048 | 1.76983 |
| 5% | 1.07483 | 1.79704 |
| **derived** (7.735% / 31.6%) | **1.14814** | **1.93083** |
| expected g₂/g₁ | **1.15470** | **1.63299** |

At the derived separation sim_Au agrees to **−0.57%** with 99.7% of positions
still contributing, and Si_SiGe **misses by +18.2%** — the check firing on the
dataset whose shell assignment really is wrong. **Stated limit, which follows
from the filter and not from the data:** because r₂ is *selected* as at least
1 + (g₂/g₁ − 1)/2 times r₁, a ratio that is too *small* cannot be detected. Only
upward mismatches are visible. That is the direction §3.2 exists to catch —
reading shell 2 as shell 1 gives g₃/g₂ > g₂/g₁ — but the asymmetry is real and
belongs in the code comment, not in a footnote nobody reads.

### The thresholds, each with the gap it sits in

- **§3.1 MAD/observed > 0.07.** The measured gap is **(0.0222, 0.2152)** —
  0.0222 is the largest value among cases whose Q result is acceptable
  (sim_Au arm B δ = 1, +1.9%), 0.2152 is real Si_SiGe as shipped. Geometric
  centre 0.0691, written as 0.07. Not a round number picked in advance: the
  gap's endpoints are in this file and move it if a later dataset says so.
- **§3.1b observed ≤ probeRadius.** Ratio 1.0, physical, unfitted.
- **§3.2 |ratio/expected − 1| > 0.03.** Gap (0.57%, 18.2%), geometric centre
  3.2%. **The sound side is ONE dataset**; this is the thinnest of the three
  and should move when a second good dataset exists.

### The layering, measured — and the one hole it leaves

The `originRMS` column was added to run the *shipped* origin-fit gate on the
same perturbed maps, so the composition is observed rather than argued from
algebra. On sim_Au the two layers meet exactly at the probe radius, with no gap:

- δ ≤ 2 px — nothing fires; q error ≤ 5%.
- 2 < δ ≤ 6.1 px — origin gate passes, **obs/probeRadius fires** (0.474, 0.802).
- δ > 6.1 px — obs/probeRadius passes (1.294 … 3.250), **origin gate BLOCKS**
  (RMS 8.00, 12.00, 20.00 against a 6.096 px radius).

Both thresholds *are* the probe radius, which is why they meet. **The hole is
the fallback, and it is not coverable by any check:** `.fileMean`/`.sessionMean`
leave `calibration.origin` nil, `originFitIsQuantitative` returns `true` when
there is no residual to judge, so the upper layer does not exist in exactly the
state where the origin is a guess. Measured magnitudes of that guess: **1.14 px
on sim_Au (0.19 × probe r)** — below the 2 px floor, invisible, +1.1% error —
and **7.07 px on Si_SiGe (1.41 × probe r)** — above the estimator's band, with
no origin gate above it. **This is why §5 item 2 has to be a structural fix and
not a check**, and it is the sharpest argument in the session for doing it
first.

## 2. E2 result — measured 2026-08-28: no defensible ceiling, and why

Harness: `tools/origin-fit-diagnostics/run.sh trim-sweep`. It calls the
**shipped** fitter (`OriginCalibration.fitOriginTrimmed` and the masked
`fitOrigin`, exposed this session for exactly this reason) so nothing measured
here can drift from what the app does.

**The pre-registered criterion, unchanged:** a ceiling is defensible at the kept
fraction where the fitted origin's own uncertainty reaches **2 px** — #29 item
1's estimator-breakdown scale.

Method note stated because it is the step a reader would otherwise guess at:
the uncertainty is *m*-out-of-*n* subsampling without replacement at *m* = *n*/2,
200 draws, scaled by √(m/n). A `Bool` inclusion mask cannot express a
with-replacement bootstrap, and using the app's own fitter was worth more than
the textbook variant.

### The app's own trim, five datasets

| dataset | kept at k = 4…1 | max bootstrap SD | max gap |
|---|---|---|---|
| `Particle_1…bin8` | 73.8% → 66.1% | 0.073 px | 9 |
| `calibrationData_circularProbe` | 99.8% → 81.1% | 0.017 px | 2 |
| `downsample_Si_SiGe_exp` | 100.0% → 80.8% | 0.243 px | 6 |
| `polycrystal_2D_WS2` | 86.4% → 77.7% | 0.000 px | 3 |
| `sim_Au_data_all_binned` | 88.1% → 68.2% | 0.002 px | 8 |

The largest fit uncertainty anywhere in that table is **0.243 px, eight times
below the criterion**, and the trim never excludes more than 34% on any real
dataset.

### Forced low fractions — because the trim could not reach the regime in question

The sweep bottoms out around two thirds kept, so on its own it cannot answer a
question about *high* exclusion. Forcing the kept fraction (keep the N smallest
residuals to the ordinary fit, refit on those) reaches the regime a ceiling
would govern:

| forced kept | Particle_1 SD | sim_Au SD | Particle_1 max gap |
|---|---|---|---|
| 60% | 0.072 px | 0.002 px | 12 |
| 20% | 0.111 px | 0.004 px | 13 |
| 5% | 0.101 px | 0.004 px | 19 |
| **2%** | **0.100 px** | **0.004 px** | 20 |

**At 2% kept — 98% excluded — the fit's own uncertainty is still two orders of
magnitude below the criterion.** A three-parameter plane over thousands of
positions is heavily over-determined, which is exactly what the pre-registration
predicted.

### The answer, and the honest limit on it

> **§6(b): no ceiling on the excluded fraction can be justified on this
> evidence.** The recommendation is to ship without one, refuse on the robust
> residual, and report the fraction — which is the branch §6(b) explicitly
> permits. **This is a recommendation the owner can overrule, not a decision
> taken for them.**

**Scoring the pre-registration.** Confirmed, and the second half of it was
initially untested: the prediction said "below 2 px even at kept fractions under
20%", and the first sweep only reached 66%. The forced sweep was added for that
reason rather than the claim being left half-verified.

**What this measurement CANNOT see, and it is the limitation that matters.**
Bootstrap SD measures the fit's *precision*, not its *bias*. At 2% kept the
plane is precisely determined by 81 mutually consistent positions and may still
be a poor description of the other 98% — and this experiment cannot detect that,
because the excluded positions have no trusted origin to compare against, which
is the whole reason they were excluded. So the finding is narrower than "no
ceiling is needed": **a ceiling justified by fit uncertainty has nowhere to go;
a ceiling justified by representativeness is neither supported nor refuted
here.** The `maxGap` column is the closest thing to a representativeness
measure and it does grow (5 → 20 scan positions on Particle_1), but at the
fractions the app's own trim actually produces it stays at 9 or below.

## 3. What shipped

Design §5's list, in its order. Item 7 (the coarse step) stayed **out**, as S12
recommended on its measurement.

1. **The robust origin fit.** `OriginCalibration.fitOriginTrimmed` — three
   rounds at median + 3·1.4826·MAD, the constants S12's numbers were measured
   with, so the app and the diagnostics that justified it trim identically.
   Marked `DEVIATION` from py4DSTEM's `fit_origin` with the reason. Both
   `tiledRun` and `run` now call it. `fit2D` gained an `included:` mask, and
   its degenerate-solve fallback averages only the included positions — an
   unmasked fallback would silently undo the trim on exactly the scans where
   the system is worst conditioned.
2. **The origin fallback.** `Calibration.recordedOriginX/Y` gives the file's or
   session's recorded beam centre a home; before this it lived only in
   `aperture.centerX/Y` and was lost the moment the user moved the detector.
   `Calibration.referenceOrigin(detectorQX:detectorQY:apertureCentre:)` is the
   one derivation, returning the value **and its kind**. The four call sites
   S11 catalogued ask it. `ResultExport` round-trips the recorded origin
   instead of the aperture.
3. **The split.** `originFitIsQuantitative` → `originFitIsSane` (looser, reads
   the **robust** residual) and `originSupportsReciprocalMetrology` (stricter,
   adds "the origin is a measured beam centre"), with
   `SessionGates.reciprocalMetrologyRefusal` as the app-level gate beside S7's
   existing one. No fifth derivation.
4. **The estimator checks.** Shell consistency, radius-vs-probe, and the
   shell-ratio self-check with the derived separation, inside
   `KnownCrystalQCalibration.estimate`. `QCalibrationShellCheck` carries
   `.agreed` / `.disagreed` / `.notSelfChecked`. The two new arguments have
   **no default value on purpose**: a caller that cannot supply them would
   otherwise get an estimate whose checks silently did not run, which is this
   repo's documented failure mode in miniature.
5. **The refusal text.** Names which failure it is, leads with manual entry,
   demotes the fit functions with the reason they cannot help.
6. **The strain-weighting provenance key** — `strain_weighting = w_r2`,
   `strain_weighting_py4dstem = w2_r2` on the strain bundle.
7. Plus the `OriginMeasure.metal` half-pixel seed, folded in as S12 asked.

**The seam** (`docs/development-process.md` §7, rule 1 — state the stage is
adding goes into its own type from the start): `App/QCalibrationRun.swift`,
`@Observable`, owning the last Q attempt's estimate, its refusal and the
self-check verdict. `AppState` holds it with no forwarding properties. It had to
exist: `.notSelfChecked` is a third state that is neither pass nor fail, and
before this everything but the number went into `statusText`, which the next
operation overwrites.

**Carried on the product**, per the owner's §6(a) decision: the calibration
panel, the Prepare readiness detail, the displayed-result metadata record, the
publication caption, and the strain and orientation bundles
(`origin_reference`, `origin_reference_is_measured`,
`origin_fit_residual_px`, `origin_fit_excluded_fraction`,
`origin_fit_positions_used_fraction`).

**Also done, not asked for:** `tools/origin-fit-diagnostics` was migrated off its
hand-written source list onto `tools/lib/sources.manifest`
(`development-process.md` §1: when next touched — it was one of the
hand-listing runners the 2026-08-17 breakage was about), and the manifest gained
a `qcalibration` group.

## 5. The finding S13 did not go looking for

**The app's own demo dataset is not consistent with the crystal model the demo
path pairs it with, and the Q calibration it produced was ~14% wrong.**

`DemoFourDDataSource.pattern` draws two spot rings, 17 px and 24.5 px, and its
own comment calls them *"{110} at 45° and {200} on-axis"*. **FCC has no allowed
{110}.** Measured on the shipped demo (probe *r* 9.649 px, 960 peaks): innermost
radius **18.67 px**, outer ring **26.66 px**, ratio **1.4275 ≈ √2** — which is
{200}/{220} of a cubic [001] zone, where `au_fcc`'s two innermost *allowed*
shells give 1.1547. Dividing g₍₁₁₁₎ by 18.67 px gives **0.0227 Å⁻¹/px against
the demo's declared 0.02**, and it was stamped `.measuredInApp`.

**This is the exact defect §3.2 was designed to catch** — the innermost
*detected* peak is not the innermost *allowed* shell — found on the app's own
onboarding fixture by the check on its first real outing.

It went unnoticed because the test that should have caught it,
`testAcceptableOriginStillCalibratesAndStampsMeasuredInApp`, asserted 0.02 with
`accuracy: 0.006` — **a 30% tolerance on the one number it existed to pin.**
That is the "green but worthless" class this repo has caught three times before,
and it was in a test whose own doc comment argued at length for asserting the
value rather than its existence.

**What S13 did, and deliberately did not do.** The check was not weakened and
the fixture was not edited (owner's call, taken in-session). The tests now
record the true behaviour, a second test pins the refusal with its numbers so
whoever fixes the fixture is told to update it, and the whole thing is an entry
in `docs/open-items.md` with **F1.42** queued so the owner sees the refusal on
screen before deciding. Refusing is the right behaviour meanwhile — recoverable,
with manual entry rendered beside it — but **the demo now demonstrates less than
it did this morning**, and that is a real cost, not a technicality.
