# C2 — the MLX training spike (2026-09-28): FAILED as registered; what it established

ROADMAP C2, pre-registered in `archive/v4/ondevice-training-research-2026-09-28.md` (four pass criteria; if 1 fails
"the mirror is wrong", if 3 fails "try the patched-package fallback, or accept GPU inference"). Code:
`tools/mlx-training-spike/` (diagnostic; MLX Swift 0.31.6 pinned in `Package.resolved`, built by xcodebuild, never
linked into the app or DSTEMCore). Inputs exported once from `tools/disk-detector`: 128 simulated training samples
(seed 20260928), 32 held-out (seed 999, disjoint draws from the same probes and backgrounds), the 16 fixture patterns
at 256 px. Model: the shipped `disk-detector-heatmap-256.mlpackage` (`0f53d270…`), its 29 conv weight/bias blobs read
from `weight.bin` (OIHW fp16 → MLX OHWI); the head bias is inline in the spec and frozen. Loss `(1 + 20 t)(p − t)²`,
AdamW (weight decay 1e-4), batch 8, 500 steps. Logs (session scratchpad): `spike-run1.log`, `-run2a`, `-run2b`,
`-run3`, `spike-fallback.log`, `c4-*.log`; predictions `run2-predictions.md`, `run3-predictions.md` (quoted below).

## How the numbers came to be (the order matters)

- **Runs 1–2 were instrumented wrongly** (independent refuter, 2026-09-28): heatmaps compared at batch 16, where
  `.all` ran on the GPU (0.0027, 5× closer to fp32 than the CPU — the GPU's signature; the ANE is 0.075 from fp32
  in the 2026-09-08 `check.json`); footprint sampled between steps, not the peak; latency timed with the input
  conversion both models share (≈ 0.23 s of it squeezed a 3.2× inference ratio to "1.18×"). Run 2 also changed lr, cache and chunking after
  run 1 failed, so it is a diagnostic, never a pass. Run 1 had no `lr`/`val_chunk` keys (an earlier revision; the
  defaults reproduce it).
- **Run 3 predictions** (`run3-predictions.md`; outcomes were appended after run 3, so the file alone cannot show
  P1–P4 came first; `main.swift` was last edited after run 3 to add the fallback — run 3's `spike.json` keys match
  the current code): P1 ANE vs MLX > 1e-2 — held (0.0355). P2 injected vs MLX on the ANE > 1e-2 —
  held (0.0591). P3 no prediction on the lifetime max — 3 339 MB, read right after training and before any criterion-3 model
  loads; no Core ML model is alive during training. The loop raised the high-water mark ≈ 1.78 GB over a 1.56 GB
  baseline (data loaded), and MLX's own active peak is 2 776 MB: MLX's training allocations alone exceed 2 GB.
  P4 injected latency ≤ 1.2× — **refuted** (3.2×).
- **Fallback predictions:** P5 the 3.2× is the in-memory path — held (patched package on disk, compiled: 0.03468 vs
  0.03467 s). P6 the on-disk and in-memory ANE heatmaps agree to ≤ 1e-3 — **refuted** (0.0034). Not nondeterminism: one
  compiled model gives bit-identical rows for the same input (i and i + 16); the two are different compile paths
  (in-memory asset vs compiled package), as their 3.2× vs 1.0× latencies also show.
- **Run 2 H-loss** held (lr 1e-5 ends ≤ its start) but its stated mechanism was false: the 2026-09-08 run stopped at
  its 90-min cap at step 6 500 of a 20 000-step OneCycle, lr ≈ 8e-4, not "near 0". Run 3's held-out loss falls to
  0.00322 by step 50 and rises back to 0.00335 by step 500: the endpoint pass depends on stopping there.
- **Python picking on the fixture** (not criterion 4): the MLX mirror's heatmap gives the run's recorded accepted counts
  and recall/precision at every threshold (307/304/295/225 accepted at 0.3/0.5/0.7/0.9; 0.773 / 0.807 at 0.7);
  candidate counts differ by up to 7. The run-2b injected model scored 0.773 / 0.818 (291 accepted), but that heatmap
  was batch 16 on `.all`, i.e. the GPU path (it equals `cpuAndGPU` to the digit), not the ANE.

## What it established

- **MLX mirrors the shipped graph** to 0.0027 on the GPU path, trains it on this Mac (0.65 s/step at batch 8,
  12 samples/s against PyTorch-MPS's ≈ 36.5 at batch 32), and the fine-tuned weights go back into the shipped Core ML
  spec with MLComputePlan preferring the Neural Engine for all 15 convs. The blobMapping key is `weights/weight.bin`
  (`@model_path/weights/weight.bin` is refused).
- **The in-memory route is 3.2× slower; the on-disk patched package is not** (speed only; its ANE accuracy fails too).
- **The 1e-2 bar did not pass on the ANE for either weight set measured**: the shipped weights are 0.0355 from their
  exact mirror, the fine-tuned 0.0591 (both on the 16 fixture patterns; `check.json` put the ANE at 0.075 from fp32
  on 256 inputs). The ANE's error depends on the weights and the inputs: a distribution, not a floor.
- **Memory fails**: MLX's own training peak is 2.78 GB at batch 8, above the 2 GB bar.
- For a model a user trains in the app, Core ML is the runtime (Core AI has no on-device writer); ADR 014's revisit
  for our own Python-trained models is untouched.

## Owed before C3 (owner decisions marked)

1. **Owner:** how a fine-tuned model is judged on the ANE: a heatmap bar would have to come from the ANE's error
   distribution over many inputs and weight sets (not the 0.0355 of one fixture), or judge by detection (recall /
   precision on held-out labels) instead of heatmap equality — or accept GPU inference for fine-tuned models.
2. A smaller training step (batch or activation memory), measured with `Memory.resetPeakMemory` before the loop.
3. Criterion 4 through the app's own `LearnedDiskDetector` path, and the on-disk package's ANE heatmap vs MLX.
4. Explain P6 (0.0034 between the in-memory and on-disk compile paths of the same weights) before any parity bar
   tighter than that.
