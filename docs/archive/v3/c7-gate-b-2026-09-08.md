**M3 — `fitOffset` rounding is a vacuous check.** The fixture's probe centre is `(63.6, 64.3)`
(`fixture/swift/expected.json`), so half-to-even and half-up agree and
`testFitOffsetMatchesPython` cannot see the rule it is named for. `windowOrigins:213` carries the
same untested mode. *Hypothesis:* assert `fitOffset((x:64.5,y:64.5)) == (-64,-64)`,
`(x:65.5,y:65.5) → row0 == -62`, `windowOrigins(q:128, probeCentreOnAxis:64.5, overlap:24) ==

`.5` (a centre of mass often does) shifts the whole model frame one pixel against Python's.

**M7 — the disagreement matcher is blind to an axis swap. Worst finding.** Every classical peak in
every test sits on **x == y**: `(10,10) (30,30) (50,50) (20,20)`
(`LearnedDiskDetectionScanTests.swift:90-93,113-114,134-136`; the helper at `:76-79` takes
`(x, y)`). With `a.x == a.y == c` the swapped distance is `√((c−b.y)²+(c−b.x)²)` — the unswapped
distance for *any* `b`. Blind by construction, not by luck. The AppState test is no better: its
classical peaks are `(0,0)` and `(1,0)`; the swap moves the losing candidate 0.8 → 1.02 px, both
inside the 2-px radius, both beaten by the 0.2-px pair (`LearnedDetectionSessionTests.swift:151-176`).
This is the repo's own recorded trap — mutation-tested suites blind at symmetric constants.
*Hypothesis:* one off-diagonal pair — classical `(x:3,y:40)` vs learned `(x:3.5,y:40)` → `matched
== 1`, `medianResidualPx == 0.5`, `image.pixels == [0]`. Under M7 the distance is `√(37²+37²)` and
the pair vanishes. Passes on pristine (I ran it).

**`learned_model_sha256` vs `export.py`'s `sha256_tree` — they CAN disagree.** `export.py:111-116`
uses `sorted(p.rglob("*") if f.is_file())`; on Python 3.12 `rglob("*")` **includes dot-prefixed
entries at every level** (verified). `sha256(ofAsset:)` at `:89` filters `!rel.hasPrefix(".")`,
which **drops a root-level dotfile** and keeps a nested one. Demonstrated on a synthetic tree: with
a root `.DS_Store` the digests differ (`eef75fd9…` vs `47e4a297…`); without it they match. Ordering
is safe (sorting relative paths ≡ sorting absolute paths under a common prefix). The shipped
package has no dot entries (`Manifest.json`, `Data/com.apple.CoreML/model.mlmodel`,
`…/weights/weight.bin`), so the rule is currently vacuous. *Hypothesis:* drop the Swift filter so
both hash everything, and make `export.py` refuse a package containing a dotfile.

## C. Replay rules — HELD
Absent `detector_class` → classical (`ReplayPlan.swift:706-713`; C1 fails 4 tests). Learned without
a threshold, or with an empty hash → refused **by key name** (`:714-721`). Wrong hash → refusal
naming **both** prefixes (`Session/LearnedDetection.swift:224-228`), reached from `AppState.swift:1878`
before the ordinary disk refusal. `replayParameters(for:)` writes `assetSHA256 ?? ""`, so a nil
hash records empty and is later refused — the safe direction.
**Minor finding:** `replayRefusal` sets `detectorClass` (`:213`) and `threshold` (`:215`) *before*
the hash guard, so a refused replay leaves the picker switched to Neural net at the recorded
threshold. No test covers state after a refusal. *Hypothesis:* assert the class is unchanged after
a refused learned replay, or move both assignments below the guard.

classical 0.7757 ms/pattern, 2017 peaks; learned **1.48×** at 0.7 (4544 peaks) and **1.48×** at 0.9

deterministic. Caveats the claim should carry:
1. **The band is noise, not resolution.** Run 1 has 0.9 *slower* than 0.7 (1.643 vs 1.437); run 2

   refine work. The classical baseline itself moved 0.832 → 0.758 → 0.776 ms/pattern. Honest
   statement: "≈1.5×, ±0.15" on an 8-core MacBook Air at median-of-3.
2. **Not quite like-for-like:** classical correlates on a 250² FFT, the learned path on 256²
   (padded). 256 is a power of two, 250 is not — a bias *in the learned side's favour*.
3. **Recording bug:** `main.swift:70` reads `learned_crop_origin_row`/`_col`, but the keys are
   `learned_crop_origin_x`/`_y` (`LearnedDiskDetector.swift:457-458`). Both archived JSONs and mine
   record `"crop_origin_row": "", "crop_origin_col": ""` — the evidence does not pin the crop
   origin it claims to.

## F. The labels wire format — **REFUTED**
`load_labels` (`evaluate.py:62-72`) accepts the app's file (frame native, positions parse). The
**caller** does not: `evaluate.py:117` and `:296-297` do `ing[f"{L['ingredient']}_probe"]` /
`_centre`. `label_centres.py:25` restricts `--ingredient` to `{bullseye, ws2}` — the npz's keys.
`DiskCentreLabels.swift:222` hardcodes `ingredient: "app"`. Executed the reader verbatim on a
hand-built app document: `load_labels OK -> [(5, 7)]`, then **`KeyError: 'app_probe'`**. So
`evaluate.py --labels <app export>` cannot run without hand-editing the JSON, and `decisions.md`'s
"`evaluate.py` and the fine-tuning step read app labels and tool labels alike" is not true as
shipped. Secondary: `seed` is always `0` (`:224`), and reading a tool file then re-exporting
rewrites `ingredient` to `"app"` and `seed` to `0` — a lossy round trip.
*Hypothesis:* carry `ingredient`/`seed` through `Document` and let the owner pick (default
`bullseye`), or have `evaluate.py` fall back to `--ingredient`; then assert the encoded
`ingredient` is a value `evaluate.py` can key on.
